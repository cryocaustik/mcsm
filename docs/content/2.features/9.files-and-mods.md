The **Files** tab manages everything that lives inside a server's data
folder: mods, plugins, their config and data files, and the world's
datapacks.

## Browse and install mods

Choose **Download mods** (or **Download plugins** on Paper), then select
[Modrinth](https://modrinth.com) or [CurseForge](https://www.curseforge.com).
Browse compatible projects or search by name, and sort by relevance, downloads,
recent updates or newest releases.

- Results are **filtered to compatible builds** — matching your server's mod
  loader (Paper, Fabric, Forge, NeoForge, …) and Minecraft version.
- **One-click install** — required dependencies are resolved and installed
  along with the mod. Dependencies already installed are skipped; conflicting
  pinned versions are reported before writing files.
- **Installed badges** — recognized projects are marked as installed. The
  server checks again before installation, so stale search results cannot
  install a second version of the same identified project.
- **Source links** — project names open their page on the selected provider.
- **Loader selection** — CurseForge modpack servers can use automatic loader
  detection or select Forge, NeoForge or Fabric explicitly.

CurseForge requires a global API key, configured by an administrator under
**Admin → Secrets → CurseForge API Key**. Browsing uses key changes immediately;
updating a key inside existing modpack containers still requires re-applying
their configuration. The key stays on the server. If an author disables
third-party downloads, use the source-page link to download the jar manually
and upload it. CurseForge does not provide Modrinth's server-side compatibility
flag, so check the project description for client-only requirements.

## Manage installed mods

The installed table shows project icons and names, filenames, installed
versions, last-modified dates, installation sources, verified provider links and
file sizes. Click a column heading to sort; use the search box and source,
availability and status filters to narrow the list. Selection is preserved across
filters, and **Select all** affects the
visible rows. Selected files can be deleted together with one restart.

- **Mod source** records how the current file was acquired: **Modrinth**,
  **CurseForge**, **Manual upload**, or **Unknown**. Jars extracted from uploaded
  ZIP bundles are manual uploads too. Downloads and newly installed dependencies
  record the selected provider. Updating through Modrinth changes the current
  file's source to Modrinth; replacing it through an upload changes it to Manual
  upload.
  The project name links to its recorded provider and uses that provider's name,
  icon and version when available. Manual uploads and files with unknown origins
  use an identified listing. If the recorded provider cannot be identified, the
  name stays unlinked; verified links remain in **Available on**.
- **Available on** links to verified listings for the exact installed jar. A
  manual upload can have links to both Modrinth and CurseForge while its source
  remains Manual upload. **Not identified** means no provider listing could be
  verified.
- **Dependency** tags identify mods installed automatically as dependencies or
  required by another recorded installation. Hover over the tag (or focus it
  with the keyboard) to see the mods that directly require it. Shared dependencies
  list every requiring mod once. Use the **Dependencies** status filter to find
  them quickly. Reusing an existing manual upload keeps its Mod source unchanged.

Dependency links are recorded for new installations from either provider and
refreshed by Modrinth updates. Removing a mod removes it from its dependencies'
hover lists. An automatically installed dependency keeps its tag when unused;
the tooltip explains that no installed mods currently require it. Dependencies
are not automatically deleted. Older installations without dependency records
do not gain inferred relationships until a new installation or update records
them.

Installation sources are saved with the server's data and survive container
recreation, server copies, backups and restores. Records are checked against the
file's SHA-1 so a file changed outside MCSM cannot keep a stale source label.
Existing jars without recorded history show **Unknown**; their source cannot be
reconstructed from provider listings. Files added directly to the volume also
show Unknown until acquired through MCSM.

Jars are identified by SHA-1 on Modrinth and by fingerprints verified against
SHA-1 on CurseForge. Manually uploaded jars are identified too. Files published
on both providers can show both links in **Available on**. Unknown/private
jars remain visible with their filenames even if a provider is unavailable.
Files larger than 100 MB remain visible but are not fingerprinted.

Routine refreshes check file metadata and reuse hashes, fingerprints and provider
matches for unchanged jars. Adding a mod normally identifies only the new files;
update checks share the same hashes. A full scan still runs on first access,
after MCSM restarts, periodically, or when you click **Refresh** to force a
recheck. Large collections can take longer during these full scans. File writes
and deletions invalidate the local listing immediately.

Duplicate checks match projects on the same provider and identical files
across providers. Different versions or different builds published on different
providers cannot always be linked automatically; review the installed list
before installing a project from the other source.

If installation fails, the download browser keeps the reason and a suggested
next step visible. Expand **Diagnostic details** for the failed step, file,
upstream HTTP status and reference ID. The reference ID matches the MCSM server
log entry and can be included in a bug report. Temporary network failures offer
**Retry installation**; **Open source page** is available for manual downloads.
API keys and raw upstream request headers are excluded from these diagnostics.

**Modrinth updates** remain available for recognized jars, including manual
uploads. Update badges and the update action currently use Modrinth; CurseForge
update management is a follow-up. Jars managed through `MODRINTH_PROJECTS` have
an **Auto-install** badge and are managed by the server image on startup.

## Export and import mod lists

Use **Files → Mod list → Export mod list** to save a JSON list. Export all mods
or only selected rows, and toggle **Include dependencies**. Optional fields
include names, installed versions, filenames, acquisition sources, source-page
links, file sizes, modification dates, and the source world's information.
Provider/project references and dependency tags remain in every export so the
list can be imported again. Exporting installed versions also saves their
provider version IDs for optional exact-version imports.

To use the list in another world in this app:

1. Open the destination world's **Files** tab and choose **Mod list → Import mod
   list**.
2. Choose the exported JSON file, review its entries, and select the mods to
   import. **Use listed versions** selects exported versions; leaving it off
   installs the latest builds compatible with the destination's loader and
   Minecraft version. An incompatible version or conflicting installed build is
   reported without replacing the existing file.
3. Start the import. Required dependencies are resolved again even if omitted
   from the list. Existing mods are retained, including their sources, and
   missing dependencies of existing mods and libraries are installed too.
4. Review each result. Failed entries keep their reason and diagnostic reference
   and can be retried. **Stop after current mod** finishes the current mod before
   stopping the remaining queue. If enabled, a running server restarts once after
   the batch adds files.

The list contains references, not jars, worlds, configuration, or API keys.
Recognized manual uploads use a verified public listing for installation; private
or unrecognized files are listed for manual upload. CurseForge entries require
the destination app's configured API key and still respect download restrictions.
Imports are additive, and successful entries remain installed if a later entry
fails. Files must be MCSM JSON exports under 2 MB with at most 1,000 entries.

## Upload your own jars

Choose **Upload files**, then drop `.jar` files (or `.zip` bundles) into the server's
mods/plugins folder — for private plugins, pre-release builds or anything not
on either provider.

## Manage files

The file manager browses the folders mods and plugins keep their files in —
`plugins/` on Paper, `config/` (plus the world's `serverconfig/`) on mod
loaders — and the active world's `datapacks/`:

- **Upload any file** into the open folder, by button or by dropping files
  onto the list — WorldEdit schematics go to `plugins/WorldEdit/schematics/`
  (Paper) or `config/worldedit/schematics/` (Fabric/Forge/NeoForge), datapacks to
  `world/datapacks/`. Files that already exist are listed before they get
  replaced.
- **Create, rename and delete** files and folders. A rename never replaces an
  existing file.
- **Download** any file, binary ones like schematics included.
- **Edit** text files in a built-in
  [Monaco](https://microsoft.github.io/monaco-editor/) editor (the editor
  that powers VS Code) with syntax highlighting for YAML, JSON, TOML and
  properties files.

::tip
Saving runs server-side YAML/JSON validation — a syntax error is rejected
with a pointer to the problem instead of being written to disk, so a typo
can't take the server down.
::

::note
`server.properties`, jars and itzg's internal dotfiles stay out of the file
manager: MCSM regenerates `server.properties` from the Configuration tab, and
jars are handled by the mod/plugin list above.
::
